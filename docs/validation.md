# 本机验证记录

## 0.2.0 独立全代理（2026-11-05）

本机原来的 Clash Mi 7890 为 rule 模式，包含国内直连规则及国内 DNS。浏览器经该入口仍可能得到国内站点直连出口。因此新增独立 Mihomo 1.19.33 内核、仅回环监听的 17890 入口、固定美国节点与唯一 MATCH 规则。网站 DNS 经节点访问 Cloudflare DoH；导入时经已有代理完成节点自身的加密解析，并固定服务器 IP，避免启动时依赖系统 DNS。节点入口变更后需重新导入。

实测（`tests/test_live_exit.py`，使用 SOCKS5 远端域名解析）：

- 新通道 Cloudflare trace：203.10.97.121，US。
- 新通道 `https://my.ip.cn/`：203.10.97.121，与海外出口相同。
- 同时保留的 7890 访问 `https://my.ip.cn/`：117.136.38.90，原有分流未被切成全局模式。
- `2026.ip138.com` 在测试时返回 HTTP 404；按检测页的备用来源使用 my.ip.cn，未把失败视为通过。
- 使用检测页实际的随机子域名及 `/api/dns/result/` 接口，观测到 104.22.50.101、104.22.194.84、162.158.185.27、172.64.216.83，页面地理接口均返回 US / Cloudflare；没有出现 CN 解析器。此结果是一次实测，不是对所有网络条件的保证。
- 两项配置回归测试及实际程序集 STA 入口检查通过；发布构建成功。
- 桌面实际点击“检测代理”，独立内核自动启动且 SOCKS5 握手通过；选择 chrome.exe 后点击“启动所选程序”，界面进入独立浏览器启动流程，使用 17890。

此次没有修改 Clash 配置、系统 DNS、路由或全局代理。发布压缩包从干净目录组装，不包含浏览器资料或节点凭据。上述在线证据来自请求测试，尚未取得新版浏览器内完整检测页截图。普通应用的系统服务代发 DNS 等边界仍保留；Claude Desktop 仍未验证。

## 0.1.1 文件选择修复（2026-11-04）

界面入口原先缺少 `[STAThread]`，未满足 Windows 文件选择窗口的线程要求。已改为显式 STA 入口，并给文件选择窗口指定主窗口作为所有者。

构建检查通过。`dotnet run --project tests/UiEntryPoint -- <RegionLauncher.dll>` 检查实际发布程序集的入口：0.1.0 失败，0.1.1 通过。本次桌面控制工具初始化报“failed to write kernel assets: 系统找不到指定的路径”，因此尚未完成实际点击、取消与文件选择验证。下方网络和浏览器结果来自 0.1.0，本次没有重跑。
